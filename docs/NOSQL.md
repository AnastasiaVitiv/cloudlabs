
Порівняння реляційної (PostgreSQL) та нереляційної (DynamoDB) БД
У проєкті реалізовано паралельний запис: сирі дані зберігаються у DynamoDB (Partition Key = sensor_id, Sort Key = measured_at), а оброблені — у PostgreSQL. 
Запит історії підтримує перемикання через параметр ?source=nosql.

Порівняння запитів історії
PostgreSQL: SELECT * FROM measurements WHERE sensor_id = $1 AND measured_at BETWEEN $2 AND $3 ORDER BY measured_at DESC LIMIT $4;
DynamoDB: Query за точним збігом sensor_id та умовою діапазону between(from, to) на measured_at із прапорцем ScanIndexForward=False.## Порівняння можливостей запитів

Історія одного датчика за часовий діапазон працює швидко в обох системах: у PostgreSQL — завдяки складеному B-Tree індексу `(sensor_id, measured_at DESC)`, а в DynamoDB — ще швидше завдяки прямому зверненню до потрібної партиції за `sensor_id` та послідовному читанню відсортованого діапазону `measured_at`.

Агрегації по всіх датчиках одночасно (наприклад, розрахунок середньої температури по місту чи підрахунок кількості повідомлень за годину) зручно виконуються в PostgreSQL стандартними операторами `GROUP BY` та `AVG()`. У DynamoDB такі запити є дорогими та повільними, оскільки вимагають повного сканування всієї таблиці (`Scan`) з вичитуванням кожного елемента.

Пошук усіх аномалій без вказання конкретного `sensor_id` у PostgreSQL виконується простим фільтром `WHERE is_anomaly = TRUE` (за потреби прискорюється частковим індексом). У DynamoDB такий запит без ключа розділу `sensor_id` неможливий без повного `Scan` або створення окремого глобального вторинного індексу (Global Secondary Index — GSI), що дублює дані та збільшує вартість запису.

Масштабування запису: у PostgreSQL впирається у вертикальні ресурси одного вузла (CPU, Disk IOPS) та ліміт активних TCP-з'єднань.
у DynamoDB автоматично розподіляє дані по фізичних партиціях за хешем sensor_id і працює по HTTP API без постійних з'єднань, масштабуючись до десятків тисяч записів за секунду без деградації затримок.
