
Обробка даних функціями
Потік даних
Емулятор -> API Gateway -> Ingest Lambda -> SQS -> Processor Lambda (batch_size=10) -> DynamoDB (raw) + PostgreSQL (processed).

Обґрунтування дизайну:
Обрано одну функцію-диспетчер, яка розгалужує логіку за полем sensor_type:

Спільний життєвий цикл: Усі датчики мають ідентичну логіку парсингу, запису в DynamoDB та PostgreSQL.

Оптимізація з'єднань з БД: Одна функція з обмеженням maximum_concurrency = 5 використовує значно менше TCP-з'єднань до PostgreSQL, ніж 4 незалежні пули функцій.

Менше холодних стартів (Cold Starts) та простіша конфігурація інфраструктури без потреби в додатковому роутері (SNS/EventBridge).

Логіка обробки за типами
temperature: перевірка фізичних меж [-60..100] °C, конвертація у Фаренгейти (value * 1.8 + 32), позначення аномалії при T > 40°C або T < -10°C.

humidity: перевірка меж [0..100] %, обчислення відхилення від норми 50%, позначення аномалії при > 85% або < 15%.

illuminance: перевірка >= 0 lux, класифікація рівня (dark, indoor, bright_daylight), позначення аномалії при > 900 lux.

camera: перевірка наявності s3_key та збереження метаданих зображення.

Забезпечення ідемпотентності
SQS гарантує доставку at-least-once (можливі дублікати). Ідемпотентність забезпечена на рівні сховищ:

У PostgreSQL створено унікальне обмеження CONSTRAINT uq_event_id UNIQUE (event_id), а вставка виконується через INSERT ... ON CONFLICT (event_id) DO NOTHING. Повторне повідомлення ігнорується без помилки.

У DynamoDB первинний ключ складається з (sensor_id, measured_at) — повторний PutItem перезаписує ідентичний елемент без створення дубля.

Обробка збоїв
Увімкнено механізм ReportBatchItemFailures. Якщо одне повідомлення в батчі з 10 штук викликає виняток, функція повертає його messageId у списку batchItemFailures. Решта 9 успішних повідомлень видаляються з черги, а проблемне повертається в SQS для повторної спроби (до 3 разів, після чого потрапляє в DLQ).
